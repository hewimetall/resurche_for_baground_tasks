# Расширяемость и сопровождение

Адаптеры одной и той же поверхности: `bench/simpleq_app.py` 298 строк, `bench/dramatiq_app.py` 229, `bench/celery_app.py` 248, `bench/arq_app.py` 235, `bench/taskiq_app.py` 211. Разница — не «насколько больно переехать», а сколько требований библиотека уже закрывает. Общая логика задач — `bench/core.py`, 163 строки, очереди она не импортирует.

## Что приходится дописывать, если нативно нет

Оценка — поверх уже написанного адаптера, горячий путь сервиса.

| Пробел | simple-q | Dramatiq | Celery | arq | taskiq |
| --- | --- | --- | --- | --- | --- |
| M4 дедуп на send | есть | лок в Redis до send, ~40 строк, и гонка «проверил / положил» остаётся | то же | ключ есть, но он не снимается на ack. Снять его своим кодом можно, ~20 строк, семантика результата arq при этом ломается | свой ключ, ~40 строк |
| M5 финальный провал | есть, включая poison | фильтр «это последняя попытка» в middleware, ~30 строк. Poison как отдельный счётчик доставок своим кодом не собрать: брокер его не ведёт | сигнал уже есть; отличить kill процесса от исключения handler нельзя | хук в `on_job_end` / исключение, ~30 строк. Poison нет | middleware, ~25 строк. Смерть процесса после ack не видна |
| M7 повтор после SIGKILL | есть | зависит от heartbeat и maintenance. Свой watchdog, который перекладывает зависшее сообщение, — отдельная очередь поверх Redis | только удлинением или укорачиванием visibility. Середины «быстро после kill и никогда при живой длинной задаче» нет | то же через `job_timeout` | то же через `idle_timeout`. Плюс выбор момента ack |
| M10 soft-память | есть | нет API. Обёртка из k8s `resources.limits` убивает под целиком, это hard, не soft | есть после задачи, не посреди неё и не по cgroup пода | нет | нет |
| M12 админка | есть | чтение ключей, ~50 строк, без гарантии схемы | `inspect`, уже в адаптере | свои команды Redis | `XINFO`, уже в адаптере |
| M13 тесты без Redis | `MemoryClient.drain` | fakeredis или мок брокера, это не drain очереди акторов | eager mode, семантика другая | нет | `InMemoryBroker`, без того же `drain` |

Чекпоинт длинной задачи — один и тот же код во всех адаптерах: `core.long_job` смотрит файл `/tmp/draining` и бросает `Draining`. У simple-q это обычный retry, ключ не перезахватывается. У Celery и arq адаптер ловит исключение и ставит retry явно. У Dramatiq и taskiq исключение само идёт в retry middleware.

## Типы, async, тесты

simple-q, arq и taskiq описывают handler как `async def`. Dramatiq тоже принимает `async def`, но исполняет его через поток с собственным циклом: блокирующий вызов в этом потоке останавливает и другие задачи того процесса. Celery остаётся синхронным, цикл создаётся в child на `worker_process_init`.

Юнит-тест без Redis есть у simple-q (`tests/test_memory_client.py`). Остальные адаптеры на стенде проверялись только процессами против настоящего Redis.

## Зрелость

simple-q `1.0.0rc7` стоит на PyPI, код — [hewimetall/simple-redis-q](https://github.com/hewimetall/simple-redis-q). Запрос лицензии к GitHub API (`/repos/hewimetall/simple-redis-q/license`) вернул 404: распознанного файла лицензии нет. Для сервиса это блокер юридический, не поведенческий: пока автор не выберет лицензию, зависимость нельзя считать разрешённой к распространению. Релиз — rc, не стабильный тег. По коду воркера сопровождение выглядит как один репозиторий. Python на стенде — 3.12.3. Заявление пакета о 3.13 этим прогоном не проверялось.

Dramatiq 2.2.1, Celery 5.7.0, arq 0.28.0 и taskiq 0.13.0 — стабильные линейки с лицензиями своих репозиториев и длинной историей выпусков. arq при этом застрял на `redis<6`, поэтому в одном venv с taskiq-redis его нет: это уже эксплуатационное ограничение, не бумажное.
