# Требования к очереди

Сервис — async Python 3.12 (FastAPI, SQLAlchemy 2 async, asyncpg, httpx, OpenTelemetry, Prometheus, Sentry). Брокер — только Redis. Деплой — Kubernetes: на очередь свой Deployment, в поде несколько процессов, память пода до 1.5 GiB, задача до 30 минут. Периодические задачи шлёт внешний APScheduler тем же клиентом очереди.

Сущности синтетические: `job`, `item`. Ниже — критерии, по которым сравниваются simple-q, Dramatiq, Celery, arq и taskiq.

## Обязательные (M)

| ID | Требование |
| --- | --- |
| M1 | Async-handler выполняется нативно, без sync-обёртки в поток или `run_until_complete`. |
| M2 | Брокер Redis. RabbitMQ не нужен. |
| M3 | На актор: очередь, `max_retries`, backoff min/max, `time_limit`, отложенная отправка (`delay`). |
| M4 | Дедуп при отправке: `send(unique_key=...)` не ставит дубль, пока задача с тем же ключом в очереди, выполняется или ждёт ретрая. Ключ снимается на ack, dead и skip. `send` сообщает, что дубль отсечён. |
| M5 | Хук окончательного провала с причиной: `retries`, `timeout`, `poison` (процесс умирал на задаче N раз). |
| M6 | Хуки процесса `on_start` / `on_stop` (пул БД), middleware вокруг выполнения (спан, контекст логов, исход задачи), заголовки сообщения (W3C `traceparent`). |
| M7 | Гибель процесса (SIGKILL, OOM): задача возвращается повторной доставкой. Счётчик доставок отдельно от ретраев. Есть порог poison. |
| M8 | Задача до 30 минут, в том числе блокирующий код, не передоставляется, пока исполнитель жив. |
| M9 | Graceful SIGTERM: перестать брать задачи и доделать текущие до grace. Сигнал не теряется в первые секунды старта. |
| M10 | Супервизор и постоянные рабочие процессы: recycle по числу задач, soft/hard лимит памяти процесса (soft — доделать задачу и уйти, hard — убить), учёт памяти пода по cgroup. |
| M11 | В handler доступно стабильное имя рабочего процесса и проверка «жив ли воркер X». |
| M12 | Интроспекция только на чтение: очереди (waiting, delayed, running, done, dead), воркеры, процессы, текущие задачи, список dead. Через Python API и CLI. |
| M13 | In-memory клиент с `drain` для unit-тестов. |
| M14 | Метрики Prometheus и проба по TCP. |

## Желательные (S)

| ID | Требование |
| --- | --- |
| S1 | Отмена выполняющейся задачи. |
| S2 | Встроенный периодический планировщик с дедупом. Сервисный путь — внешний APScheduler и тот же клиент. |
| S3 | group / chain / chord. |
| S4 | Rate limit и ограничение конкурентности по ключу. |
| S5 | Хранение результата задачи. Для сервиса не нужно, только отметить, есть ли оно. |

## Нагрузка, по которой проверяются требования

1. Цепочка: 3–5 шагов по одному объекту, шаг сам ставит следующий, часть шагов с задержкой.
2. Пачка: задача ставит N коротких задач (N от 10 до 1000). Завершение — средствами библиотеки (group, chord) и своим счётчиком в БД.
3. Долгая задача до 30 минут: asyncio и блокирующий код. На стенде 30 минут эмулируются 5 минутами из шагов по 5 секунд там, где прогон это успел. Более короткие шкалы помечены в JSON.
4. Периодические задачи с дедупом.

Инвариант: каждый элемент обработан ровно один раз. Результат пишется в Postgres, внешний side effect — HTTP в mock. После прогона считаются потери и дубли. Отмена — флаг объекта в БД, задача проверяет его перед элементом. После исчерпания ретраев, таймаута или poison вызывается хук провала, объект становится `failed`.

## Как отмечать ячейку матрицы

- **нативно** — есть в библиотеке этой версии, без своего кода в горячем пути;
- **конфигурация** — включается опцией или флагом;
- **свой код** — оценка строк, если нативно нет и это можно дописать;
- **невозможно** — библиотека этого не даёт, либо семантика другая и своим кодом её не повторить без отдельной очереди.

Измеренное на стенде и прочитанное в коде в матрице и отчётах разделены.
