# Почему Dramatiq опрашивает и спит

Числа 2.2.1 — в {doc}`/reference/dramatiq`. Сравнение с 1.18 — в {doc}`/explanation/dramatiq-1.18`.

Потребитель Redis не оставляет команду висеть в Redis. `do_fetch` делает `LPOP` и возвращается. Пустой ответ увеличивает `misses` и вызывает `time.sleep`. Поток в этот момент в `hrtimer_nanosleep`. py-spy показывает кадр `time.sleep` в `_RedisConsumer.__next__`. Байткод Python на этом потоке не исполняется, GIL у других потоков свободен. Рядом `EventLoopThread` стоит в `epoll`: это цикл для async-акторов, он список `dramatiq:bench` не читает. `WorkerThread` стоит на `queue.Queue.get` и тоже Redis не читает.

Сон растёт, пока промахи идут подряд, и упирается в `timeout`, который воркер передал в `consume`. Это `worker_timeout`, по умолчанию 1000 мс. Параметр по умолчанию у самого метода `consume` равен 5000 и на процесс воркера не влияет, пока его явно не подставят.

Пока сон ещё короткий, `LPOP` идёт часто. За окно монитор насчитал 68 `LPOP`: начало прогрессии и второй потребитель очереди `.DQ`. При `--threads 1` prefetch очереди равен 2, поэтому удачный `fetch` делает два `LPOP` подряд.

557 мс до `fast_record` — не длина сна. В `results/traces/dramatiq.monitor.txt` `RPUSH` стоит на 173 мс позже `sent_ms`, успешный `LPOP` — через 382 мс после `RPUSH`. Интервал `LPOP` по `dramatiq:bench`, внутрь которого попала постановка, равен 985 мс, и 602 мс из них уже прошли до `RPUSH`. После этого попадания паузы снова короткие (10, 12, 27, 44, 120, 162 мс) и затем возвращаются в полосу 516–965 мс. Это сон с потолком 1000 мс плюс круг до Redis. Один такой интервал — одно наблюдение, не распределение.

На короткой пачке очередь не пустеет, `misses` сбрасывается, и p50 119 мс (`docs/bench.md`) сидит в миллисекундах. Тот же воркер, оставленный пустым на секунды, уже спит долями секунды до целой секунды. Пачка из 80 задач этого потолка не показывает.

Подписки на список очереди нет. `PUBLISH` постановка Dramatiq для этой очереди не шлёт: монитор после send показывает `RPUSH`.
