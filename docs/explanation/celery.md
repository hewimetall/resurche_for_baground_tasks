# Почему Celery забирает задачу за доли секунды

Числа — в {doc}`/reference/celery`.

Родительский процесс держит сокет в поллере kombu и отправляет `BRPOP` с таймаутом 1 с. Пока Redis ждёт элемент, поток родителя стоит в `epoll`. Это один поток. GIL на время `epoll_wait` не занят исполнением байткода: кадр py-spy — `_epoll.poll`.

Ребёнок пула в это время читает пайп billiard и в Redis не ходит. Задачу из Redis забирает родитель, потом отдаёт её в пул. 230 мс в этом прогоне включают и остаток `BRPOP`, и эту передачу, и `fast_record`. Разобрать 230 мс на эти три части один файл задержки не умеет.

`--without-gossip --without-mingle` убирает рассылку состояния. `PSUBSCRIBE` на `celery.pidbox` при этом остаётся: пульт слушает свой шаблон. Очередь `bench` он не будит. Будит `BRPOP`.

`SUBSCRIBE` на ключ результата в том же `MONITOR` принадлежит отправителю `bench.cli`. Если вычесть его из картины воркера, остаётся `BRPOP` родителя и пайп ребёнка.

Короткая пачка 244/с и p50 17 мс (`docs/bench.md`) с этим согласуется: сообщение, пришедшее в уже висящий `BRPOP`, Redis отдаёт сразу, без периода heartbeat.
