# Короткий burst `fast`

Класс `stress`. `counts_as_2400` ложный. Это не контроль на 2400 с и не выбор backend.

Операция одна и та же у пяти библиотек: актор `fast` вызывает `bench.core.fast_record`. Функция дописывает строку `n,sent_ms,now_ms` в `LAT_PATH`. HTTP и запись в Postgres на этом пути нет. `open_deps` при старте воркера всё равно требует `PG_DSN` и `MOCK_URL`; оба указывают на стенд `longrun` и `127.0.0.1:6411`, запрос туда `fast` не делает.

Redis `127.0.0.1:6412`, каталог `results/long/stress-redis-6412`. Порты 6379 и 6380 не открывались и не чистились. Перед постановкой `FLUSHDB` только после `CONFIG GET dir` этого каталога. После прогона `SHUTDOWN SAVE` только этого экземпляра. Библиотеки шли по одной. Лимита cgroup нет, хост общий.

Слоты, которые задал раннер, везде 8:

| Библиотека | Команда |
| --- | --- |
| simple-q 1.2.0 | `.venv-sq120`: 2 процесса, `--concurrency 4`, `--max-tasks-per-process 20000` |
| Dramatiq 2.2.1 | 2 процесса, `--threads 4` |
| Celery 5.7.0 | `-c 8` |
| arq 0.28.0 | один процесс, `ARQ_MAX_JOBS=8` |
| taskiq 0.13.0 | `--workers 2`, `--max-async-tasks 4`, `--max-prefetch 8`, `--ack-type when_executed` |

Исследовательский `.venv` остался на simple-q 1.0.0rc7. Версии в манифесте — это `importlib.metadata` интерпретатора, который ставил задачи. У Dramatiq, Celery и taskiq этот интерпретатор — общий `.venv`, поэтому в блобе рядом лежат и неисполнявшиеся пакеты. Исполняемый файл указан в `command`.

Код адаптеров на момент старта процессов — коммит `c81f29f`. Раннер `scripts/stress_run.py` в тот момент ещё не был закоммичен. Сводка пересобирается командой `python scripts/stress_report.py` и пишется в `results/long/stress/summary.json`.

Прогон на 30 задач, `st-20261113T202833Z-simpleq-burst-30`, проверял проводку simple-q 1.2.0. Ниже — пять прогонов по 5000. У каждого `n` от 0 до 4999 встречается один раз, лишних строк нет, воркер до дедлайна 180 с не завершился сам. Статус `passed`.

`span` в манифесте — от первой `sent_ms` до последней `now_ms` в файле задержек. Окно постановки и окно завершений пересчитывает `stress_report.py` по тем же строкам. Задач/с — `unique_n / span`. Это скорость всего burst, включая ожидание в очереди, а не время тела `fast_record`.

Журналы:

- simple-q: 5000 строк `running actor` и 5000 `deliveries=1`, других `deliveries=` нет.
- Celery: 5000 `received` и 5000 `succeeded`. Строк `retry` нет. В логе `concurrency: 8 (prefork)`.
- taskiq: 5000 строк с `executing`.
- Dramatiq пишет готовность двух процессов и не пишет строку на каждую задачу. Счётчик здесь — файл задержек.
- arq: 5000 строк завершения `:fast`. В начале файла длительность handler `0.00s`. p50 12062 мс поэтому очередь, не тело задачи. `WorkerSettings` не задаёт `poll_delay` и `queue_read_limit`. В установленном arq 0.28.0 умолчания — `poll_delay` 0.5 с и `queue_read_limit = max(max_jobs * 5, 100)`. При `ARQ_MAX_JOBS=8` предел чтения 100. Сам прогон интервалы poll не записывал, так что 24.651 с на эти умолчания не разложены. Лог воркера число `max_jobs` не печатает: 8 — значение, которое раннер положил в окружение.

Сэмпл брокера у taskiq один, в конце, и равен 5000. Команда сэмпла — `XLEN`. Для стрима это длина, не `XPENDING`. Подтверждение `XACK` в этом burst не снималось.

Пик RSS по сэмплам `ps`: simple-q 159588 КБ, Dramatiq 132688 КБ, Celery 487996 КБ, arq 40576 КБ, taskiq 176804 КБ. Сэмплы редкие: у taskiq он один, уже после 5000 строк.

Строка старта arq сообщает `redis_version=7.0.15`. Остальные прогоны поднимали тот же `redis-server` через `ensure_redis` и свою версию в лог не писали.

Каталог данных Redis в git не входит. Сырые строки, манифест, сэмплы и лог воркера лежат в `results/long/stress/<run_id>/`.
