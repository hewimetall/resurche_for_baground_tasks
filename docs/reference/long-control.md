Короткий процесс, который сам выходит по SIGTERM, после сигнала остаётся зомби: `kill(pid, 0)` успешен, состояние `/proc` — `Z`, а `poll()` возвращает 0 и процесс исчезает (`results/long/stop-group-probe.json`, класс `short_bench`, не зачёт 2400 с). Эти записи длинных прогонов не доказывают зависание библиотек. Корректность определения завершения leader и всей process group на тех прогонах не проверена.

## Что подтверждено и что нет

| Библиотека | Что подтверждено | Что не доказано |
| --- | --- | --- |
| Celery | При `visibility_timeout` 2100 с сообщение вернулось в очередь до завершения живого handler и затем выполнилось повторно | Параллельный дубль на втором worker |
| taskiq | Одна длинная задача завершилась, pending исчез после завершения. В отдельном kill на порту 6396 recovery за окно наблюдения не состоялся | Защита живой задачи от reclaim другим consumer |
| Dramatiq | Живой worker удержал задачу. При принудительном maintenance recovery наблюдался | Распределение времени recovery при штатном maintenance |
| simple-q | Async-handler завершился одной доставкой. Отдельно описан бюджет Python ping | 40 минут при заблокированном loop и recovery после kill в этой длинной матрице |
| arq | При timeout 3000 с один handler и один in-progress key до завершения | Блокировка loop, истечение владения и второй исполнитель |

Однопроцессный контроль не разделяет ложный reclaim живой работы и настоящий recovery после смерти владельца. Для этого нужны два запуска: два исполнителя и задача дольше окна владения, затем отдельный запуск со смертью владельца.

Эти прогоны задают требования к дальнейшей реализации и не выбирают backend, в том числе Oxana:

- владение живой задачей не должно истекать незаметно для исполнителя;
- смерть процесса должна приводить к восстановлению за проверяемое время;
- зависший Python не должен бесконечно прикрываться здоровым Tokio heartbeat;
- прикладные retries и аварийные redeliveries нужно считать раздельно;
- shutdown нужно измерять отдельно от успешного handler.
