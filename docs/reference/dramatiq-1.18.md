# Dramatiq 1.18.0 и 2.2.1: что отличается и что измерено

Дерево 1.18.0 сверено с установленным 2.2.1. Прогон: `results/traces/dramatiq-118.json`.
Redis 7.0.15, порт 6392. Интерпретатор 1.18: `/tmp/venv-d118`, redis-py 5.3.1. Воркер на этой паре поднялся и забрал сообщения.

Формула: [PR 721](https://github.com/Bogdanp/dramatiq/pull/721), [issue 651](https://github.com/Bogdanp/dramatiq/issues/651), changelog 2.0.0.
Порядок prefetch: [issue 850](https://github.com/Bogdanp/dramatiq/issues/850), [PR 857](https://github.com/Bogdanp/dramatiq/pull/857), релиз 2.2.0.
Скрипт ack: [PR 771](https://github.com/Bogdanp/dramatiq/pull/771). Аргументы `requeue_deadline` и `requeue_interval`: [PR 782](https://github.com/Bogdanp/dramatiq/pull/782).

## Код

| Место | 1.18.0 | 2.2.1 |
| --- | --- | --- |
| `_RedisConsumer.__next__` | `do_fetch`, затем `time.sleep` | то же |
| `ConsumerThread.run` | `consume(..., timeout=worker_timeout)`, по умолчанию 1000 | то же |
| `compute_backoff`, jitter | сначала `min(factor * 2**n, max)`, потом половина плюс `uniform(0, половина)` | база без потолка, jitter `uniform(1, 2)`, выше потолка — `uniform(0.5, 1) * max` |
| `dispatch.lua` | в конце обслуживания переносит старый zset `.acks` в множество | этот блок удалён |
| `RedisBroker.__init__` | принимает `requeue_deadline` и `requeue_interval` и ничего с ними не делает | аргументов нет |
| `work_queue` | `PriorityQueue` по приоритету актора | `_WorkQueueItem` сравнивает `(priority, monotonic_ns)` |
| `AsyncIO` / `EventLoopThread` | цикл в отдельном потоке | то же |

`consume(timeout=5000)` — значение параметра метода. Воркер его не использует. Оба прогона шли с умолчанием 1000 мс.

## Формула, 2000 и 400 бросков, `max_backoff=5000`

Это не таймаут воркера. Так считается функция сама по себе.

| Версия | первый сон, мин / p50 / макс, мс | после 24 промахов, мин / p50 / макс, мс |
| --- | --- | --- |
| 1.18.0 | 2 / 3 / 4 | 2501 / 3675 / 4993 |
| 2.2.1 | 5 / 7 / 9 | 2504 / 3665 / 4994 |

Первый сон 1.18 ниже `factor` 5. Первый сон 2.2.1 не ниже 5. На потолке обе версии попадают в половину–целое от `max_backoff`.

## Живой воркер, очередь `bench`, один поток

`pickup_ms` после старта. Холодный простой 1.5 с, прогретый 16 с. Три запуска.

| Версия | холодные, мс | после 16 с простоя, мс |
| --- | --- | --- |
| 1.18.0 | 192.4, 393.4, 623.7 | 132.5, 254.8, 563.1 |
| 2.2.1 | 87.1, 492.5, 368.1 | 167.3, 259.7, 776.5 |

`MONITOR` одного прогретого запуска каждой версии: `EVALSHA` и `LPOP` (62 и 57), один `RPUSH` на send. `BRPOP` нет.

Все шесть прогретых задержек короче 1000 мс. Это совпадает с потолком `worker_timeout`, а не с выборкой формулы при `max_backoff=5000`.

## Чего этот прогон не делал

Порядок сообщений при prefetch больше 1 не гонялся. Issue 850 воспроизведён здесь не был: в коде 2.2.1 сравнение другое, на стенде пачки не было.
Миграция старых ack с версии до 1.2 не гонялась. На чистом Redis 7 её запускать не на чем.
Потолок `redis` у 2.2.1 в changelog поднят до 8.x. Прогон 1.18 шёл на redis-py 5.3.1 и сервере 7.0.15, и этот конкретный воркер команды выполнял.
