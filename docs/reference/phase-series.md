# Серия фазы и разрез до команды Redis

Один `pickup_ms` — попадание в уже идущий период. Здесь тот же воркер живёт всю серию, а момент постановки сдвигается.

`sent_ms` берётся в родительском процессе до запуска `python -m bench.cli enqueue`. В `pickup_ms` поэтому входит старт интерпретатора и импорт библиотеки, и только потом ожидание воркера.

## Протокол

`scripts/idle_dist.py`, Redis `127.0.0.1:6393`, `FLUSHALL` в начале каждой серии. Порт 6379 не использовался.

После `fast_record` скрипт спит `park_s`, затем ещё `phase`, и ставит следующую задачу. Первая точка серии предыдущего fetch не имеет. Сумма `phase + pickup` для неё не считается.

Поле `enqueue_ms` в `results/traces/idle-dist.json` — часы родителя от `sent_ms` до появления строки в файле. Ожидание воркера в него входит. Время одного только процесса постановки лежит отдельно, в `client_ms` файла `results/traces/push-to-pop.json`.

`scripts/push_to_pop.py` пишет `MONITOR` на `127.0.0.1:6391`. `client_ms` — стена `subprocess` до его выхода, файл задержки после этого не ждётся. Первый запуск оставил на 6391 осиротевший процесс arq и `redis-cli MONITOR`. Прогоны Celery, taskiq, Dramatiq и simple-q в JSON — с одним своим воркером; команды `arq:queue` того осиротевшего процесса из их списков убраны. Прогон arq в том же JSON снят заново, после того как осиротевший процесс был убит.

Дата: 2026-11-13. CPython 3.12.3, Redis 7.0.15.
